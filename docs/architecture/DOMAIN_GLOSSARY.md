# Domain Glossary — Anilya ERP

Terms as actually used in the codebase (not idealized definitions) — where the code's usage is ambiguous or inconsistent, that's noted, since the blueprint asks Phase 0 to surface contradictions rather than paper over them.

| Term | Meaning in this system | Note |
|---|---|---|
| **Order** | One customer print job, from Booking Portal import to Delivered. Single-line by design (`order_line_id` is synthesized as `orderId + '-L1'`) — the system was never built for true multi-line orders. | If real multi-item orders are needed later, this synthesis strategy needs revisiting, not just extending. |
| **Job** | A unit of work on an order (Artwork, Printing, or any ad-hoc Lamination/Cutting/Binding). One order can have many jobs; all must be `Completed` before QC-pass. | |
| **Display Job Number / Display Order Number** | The customer-facing reference (`ANILYA/YYYY/MM/#####`), distinct from the internal order ID. Used interchangeably in different parts of the codebase — "Job Number" and "Order Number" refer to the *same field*. | Worth standardizing on ONE name before the rebuild; the ambiguity is harmless today only because there's no true multi-job-per-order case yet. |
| **Master Order ID** | The Booking Portal's own order grouping reference, stored but not used for any internal logic beyond pass-through/display. | |
| **AMS (Artwork Management System)** | Conceptually an *external* system in the source requirement documents, but never actually built as one — it is fully simulated inside this same Express app via bridge-style endpoints (export/import-sync pairs) that a real AMS would call. | This is the single biggest "pretend it's external" seam in the whole prototype — see INTEGRATION_CATALOG. |
| **Customer-Approved Artwork vs. Final Internal Approved Artwork** | Two *deliberately different* things, the most safety-critical distinction in the artwork domain. Customer approval (`final_artwork_url`) is locked as historical reference and NEVER used for printing. Only `final_internal_approved_artwork` (set after the Operator + Supervisor internal cycle) unlocks `start-production`. | Preserve this distinction exactly in any rebuild — it was added specifically because the original behavior violated it. |
| **Gang Run** | Combining multiple orders' Printing jobs into one physical print run. Has its own temporary ID (`gang_runs.id`, doubling as "Shadow Job ID" and "temporary_gang_run_id" in different requirement documents — same field). | |
| **Ticket (Complaint)** | Post-delivery only. `CMP-YYYY-NNNNNN`. Deliberately NOT the same thing as a "support ticket" raised for Extra Services payment issues (`support_tickets` table) — two separate ticket concepts exist in the schema. | Naming collision risk: two different "ticket" tables (`complaint_tickets`, `support_tickets`) for two different purposes. |
| **Operator (Artwork Operator)** | A payee identity tracked via `artwork_operators` + `operator_ledger` for payment purposes — distinct from "Operator" as used in the AMS stage names (`ARTWORK_VERIFIER`/`ARTWORK_CREATOR`/`FINAL_ARTWORK_INSPECTOR`), which refers to a role/action, not this specific identity record. | |
| **Partner** | Any external vendor: Printer, Supplier, Processor (lamination/finishing), Courier, or Binder. Distinguished by `capability_types`, not a fixed enum — new partner types need no schema change. | |
| **Reservation (Inventory)** | A hold against physical stock for one order line, in the *separate* Inventory Phase 1 module — not to be confused with anything in the core order/job domain. | Inventory module deliberately keeps its own vocabulary/tables isolated from the core ERP, per its own source spec. |
| **Ledger** | Three distinct, non-interchangeable ledgers exist: Customer Ledger (what the customer owes), Operator Ledger (what the business owes an Artwork Operator), Inventory Ledger (stock movement, in the separate Inventory module). | Never assume "the ledger" without specifying which. |
| **Stage vs. Status** | "Stage" = the order's position in the 14-step lifecycle (`orders.stage`). "Status" = used loosely elsewhere for job status, ticket status, delivery status, etc. — not a single controlled vocabulary. | |
